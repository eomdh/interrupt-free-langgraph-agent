# ADR 0001 — `interrupt()` 없이, 매 POST를 1턴으로 처리한다

- **상태**: 채택
- **관련**: ADR 0002

## 맥락

이 에이전트의 워커들(온보딩·성과 분석·인터뷰·초안·채점)은 대부분 **묻고 기다렸다가 이어가는** self-loop다. 사람의 답을 받아야 다음이 진행된다.

LangGraph의 표준 해법은 `interrupt()`로 그래프를 멈추고 `Command(resume=...)`로 재개하는 것이다. 오케스트레이션이 그래프 안에 유지되고 추가 인프라가 없다는 게 매력이다.

문제는 **웹 앱의 수명주기와 안 맞는다**는 것이다. 브라우저는 언제든 새로고침되고, 사용자는 탭을 닫았다가 다음 날 돌아온다. 멈춰 있는 그래프를 그 사이에 어떻게 들고 있을 것인가가 곧바로 문제가 된다.

## 결정

`interrupt()`를 쓰지 않는다. **HTTP POST 한 번 = `ainvoke` 한 번 = START→router→(워커)→END.**

질문이 필요하면 노드가 그냥 `AIMessage`를 상태에 남기고 END로 빠져나온다. 그리고 다음 POST를 기다린다. 재개 신호 같은 건 없다 — 다음 POST가 곧 재개다.

```
POST #1  START → router → interview  → AIMessage("어떤 문제를 풀었나요?") → END
POST #2  START → router → interview  → AIMessage("그때 대안은 뭐였나요?")  → END
POST #3  START → router → draft ⇄ tag → AIMessage(초안)                  → END
```

## 근거

**질문이 일반 메시지라서 체크포인터가 전부 보관한다.** `interrupt` 지점은 재개를 위한 특수 상태지만, `AIMessage`는 그냥 대화 기록이다. 그래서 새로고침 복원이 **별도 구현 없이 따라온다** — 스레드의 메시지를 읽으면 그게 곧 화면이다. 복원 기능을 따로 만들지 않았는데 생겼다는 게 이 설계의 실질적 이득이다.

**앱이 무상태가 된다.** 진행 중인 그래프를 프로세스 메모리에 들고 있을 필요가 없다. 상태는 전부 체크포인터에 있고, FastAPI는 아무것도 기억하지 않는다. 인스턴스를 재시작해도, 여러 대로 늘려도 영향이 없다.

**재실행 함정이 사라진다.** `interrupt` 노드는 재개 시 노드 앞부분이 다시 실행되는 replay 의미론을 갖는다. 그 안에서 부작용(외부 호출·카운터 증가)을 다루려면 멱등성을 따로 신경 써야 한다. 한 번의 실행이 END까지 끝나면 그 문제 자체가 없다.

## 대안

**`interrupt()` + `Command(resume)`** — LangGraph 표준. 다중 턴 흐름을 그래프 하나로 표현할 수 있다는 게 진짜 장점이다. 다만 위의 세 가지를 전부 직접 감당해야 한다.

**외부 상태 머신 + 무상태 그래프** — 대화 단계를 앱 코드가 들고, 그래프는 단발 작업만. 오케스트레이션이 그래프 밖으로 새어나가 LangGraph를 쓸 이유가 옅어진다.

## 결과

**얻는 것** — 새로고침 복원이 공짜. 무상태 앱. replay 함정 없음. 흐름을 HTTP 요청 단위로 추론할 수 있어 디버깅이 쉽다.

**감수하는 것** — **한 요청 안에서 사람 입력을 두 번 받아야 하는 흐름은 표현하기 어렵다.** "한 턴에 끝나는 작업"만 자연스럽다. 그런 흐름이 필요하면 상태 표식(`awaiting`)으로 다음 POST를 유도해야 하고, 그건 그래프가 아니라 상태 필드로 관리된다. 이 앱의 흐름이 대부분 단발 질의응답이라 받아들인 제약이다. **다중 턴 트랜잭션이 필요해지면 이 ADR을 대체해야 한다.**

라우터가 매 POST마다 진입점이 되므로 **라우터가 뚱뚱해진다.** intent와 상태 게이트를 한곳에서 판정하게 되는데, 이건 의도한 집중이다 (ADR 0002).
