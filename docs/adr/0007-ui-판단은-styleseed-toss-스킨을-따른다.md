# ADR 0007 — UI 판단은 StyleSeed 의 룰과 toss 스킨을 따른다

- **상태**: 채택
- **관련**: ADR 0006

## 맥락

마일스톤 6에서 프론트를 붙인다. 백엔드는 줄곧 의존성을 깎는 쪽으로 갔다 — 제공자별 SDK를 안 쓰고(ADR 0004의 RAG 제외와 같은 논리), 라이브러리보다 계약을 골랐다. 그 톤을 그대로 밀면 프론트도 순수 CSS가 맞다. 처음 계획이 실제로 그랬다.

문제는 **이 앱의 화면이 단순한 챗이 아니라는 것**이다. 자율 루프가 도는 걸 보여주는 진행 스텝퍼, 5축 채점표, 동의 게이트를 여는 액션 칩 — 상태가 많고 상태마다 시각 언어가 필요하다. 통과·미달·차단·채점 중이 각각 어떻게 보여야 하는가. 활성 노드와 지나간 노드를 무엇으로 가르는가.

디자이너가 없다. 그러면 그 판단을 어디서 가져오는가. 판단 없이 만들면 컴포넌트마다 즉흥이 되고, 즉흥이 쌓이면 "그럴듯한데 조잡한" 화면이 된다. **백엔드에서는 되돌리기 비싼 판단을 ADR로 고정해 왔는데, UI 판단만 고정하지 않을 이유가 없다.**

## 결정

[StyleSeed](https://github.com/bitjaru/styleseed)의 디자인 룰과 **toss 스킨**을 따른다. 부분 채택이다.

| 층위 | 채택 | 비고 |
|---|:---:|---|
| 디자인 룰(74) — 판단 | ✅ | 이 채택의 핵심 |
| 스킨 `theme.css` (**toss**) | ✅ | CSS 변수 한 겹 |
| Tailwind v4 | ✅ | 스킨이 `@theme` 로 유틸을 생성 |
| `/ss-*` 품질게이트 | ✅ | 컴포넌트마다 review·score·a11y |
| **48 컴포넌트 라이브러리** | ❌ | 통짜 도입 안 함 — 필요분만 룰 따라 생성 |

확정값은 `web/STYLESEED.md` 에 **잠근다**(accent·radius·다크·폰트·상태 표시 규칙). 드리프트 방지가 목적이라 UI 작업은 매번 그 파일을 먼저 읽는다.

**엔진 문서와 스킬은 커밋하지 않는다.** 로컬 도구이고, `.gitignore` 의 "AI tooling exhaust" 규약을 따른다. 이 repo에 남는 것은 결정(이 문서)과 확정값(`STYLESEED.md`)뿐이다.

상태 표시는 **색 단독을 금지**한다 — 아이콘과 라벨을 함께 쓴다.

## 근거

**판단과 취향을 분리할 수 있다.** 룰(74개)은 판단이고 스킨(토큰)은 취향이다. 스킨은 CSS 변수 한 겹이라 갈아끼워도 룰은 그대로 남는다. `OPENAI_BASE_URL` 하나로 제공자를 갈아끼우면서 노드 계약은 안 건드린 것과 같은 구조다 — 바뀔 것을 얇은 층에 몰아두는 것.

**toss 인 이유.** 성과 리뷰는 한국어가 주 콘텐츠다. 한글 가독성과 톤이 맞고, 한 accent + 그레이스케일이라 채점 상태색(good·warn·danger)이 accent 와 안 겹친다 — 5축 채점표가 이 앱의 핵심 화면이라 그 분리가 실제로 필요하다.

**à la carte 인 이유.** 컴포넌트가 여섯 남짓이다. 48개 라이브러리는 대시보드 전제라 이 규모에 안 맞고, 무엇보다 스텝퍼·채점표처럼 **이 앱 고유의 UI 는 어차피 직접 만들어야 한다.** 관리 규약 §8.2 와 같은 논리로, 안 쓰는 것을 들고 있으면 시그널이 희석된다.

## 대안

**순수 CSS + 직접 토큰** — 의존성 0이라 백엔드 톤과 가장 일관되고, 처음 계획이 이것이었다. 버린 이유는 **판단의 출처가 없어서다.** 색과 간격을 직접 고르는 순간 그게 왜 그 값인지 설명할 근거가 없고, 상태가 많은 화면에서 그 즉흥이 누적된다. 의존성을 아끼려다 결과물의 질을 잃는 교환이었다.

**컴포넌트 라이브러리 통짜 도입**(MUI 등) — 화면은 빨리 나오지만 앱이 그 라이브러리의 얼굴이 된다. 그리고 스텝퍼·채점표는 어차피 직접 만들어야 해서, 정작 어려운 부분은 안 덜어준다.

**StyleSeed 를 48컴포넌트까지 전부** — 룰만 빌리는 것보다 일관되지만 규모가 안 맞는다. 위 표의 ❌ 그대로.

## 결과

**얻는 것** — UI 판단이 문서로 고정된다. 매 컴포넌트를 즉흥으로 정하지 않고 `STYLESEED.md` 와 룰을 근거로 정한다. 스킨 교체는 토큰 한 겹이고, 상태 표시 규칙(아이콘+라벨)은 접근성 문제까지 같이 닫는다. 품질게이트로 컴포넌트마다 점수를 재서, 테스트 커버리지처럼 UI 질을 추적할 수 있다.

**감수하는 것** — **백엔드보다 무겁다.** Tailwind v4 와 프론트 빌드 체인이 들어오고, 이건 "의존성을 깎는다"는 이 repo 의 톤과 정직하게 말해 어긋난다. à la carte 로 줄였지만 상쇄되지는 않는다. 디자인 판단을 사는 값으로 받아들인 것이고, 프론트가 여섯 컴포넌트를 넘어가면 이 거래는 더 유리해지지만 지금 시점에는 얇은 손해다.

그리고 **엔진을 커밋하지 않기로 해서 이 repo 만 클론한 사람은 74룰 본문을 못 본다.** `STYLESEED.md` 의 요약과 이 문서가 그 간극을 메워야 하고, 메우지 못하면 "룰을 따랐다"는 주장만 남는다. `/ss-*` 스킬도 Claude Code 환경에서만 돌아서, 품질게이트는 재현 가능한 CI 가 아니라 **작업 시점의 규율**에 가깝다 — 이건 테스트로 고정한 백엔드와 다른 층위의 보증이다.
